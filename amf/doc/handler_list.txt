Handler entry points in internal/ where a request first arrives at AMF code
AND its information elements (IEs) become visible as typed/decoded fields.

Method: for each ingress interface, picked the single innermost chokepoint
common to all messages on that interface (if one exists), instead of every
function in the call chain. NGAP and NAS each funnel every message through
one decode-then-dispatch function, so one entry each covers 100% of that
interface's traffic. SBI has no such shared chokepoint -- each Namf_*/
callback operation deserializes its own distinct request body -- so it is
one entry per exposed HTTP operation.

================================================================================
N2 / NGAP  (gNB -> AMF, SCTP)
================================================================================
1 function covers 100% of NGAP traffic (all ~30 procedure codes).

  ngap.dispatchMain
  internal/ngap/dispatcher_generated.go:10
  func dispatchMain(ran *context.AmfRan, message *ngapType.NGAPPDU)
  -> `message` is the fully ASN.1-decoded NGAP PDU; every IE for whichever
     procedure arrived (InitialUEMessage, UplinkNASTransport, HandoverRequired,
     PDUSessionResourceSetupResponse, ...) is already populated as typed struct
     fields at this point.

================================================================================
NAS  (UE -> AMF, carried inside NGAP NAS-PDU, or replayed via SBI N1MessageNotify)
================================================================================
1 function covers 100% of NAS traffic regardless of transport path.

  nas.Dispatch
  internal/nas/dispatch.go:15
  func Dispatch(ue *context.AmfUe, accessType models.AccessType, procedureCode int64, msg *nas.Message) error
  -> `msg.GmmMessage` is the deciphered, integrity-checked, fully decoded NAS
     message (RegistrationRequest, AuthenticationResponse, SecurityModeComplete,
     ...); this is downstream of nas_security.Decode so ciphering/MAC are
     already stripped and every NAS IE is a typed field.

================================================================================
SBI  (other NFs -> AMF, HTTP/JSON: AUSF/UDM/PCF/SMF/NRF-callback + OAM)
================================================================================
No shared decode point exists -- each operation has its own request model, so
these are the minimal 1:1 set (35 functions, one per exposed operation). Each
does c.GetRawData() + openapi.Deserialize() into the named models.* struct
immediately before calling into the processor package; that's where the IEs
become visible.

(X) = important to trace, per analysis/amf_state_machine.py. That graph
models the registration FSM from the *new* AMF's point of view; almost all
AUSF/UDM/PCF/SMF edges in it are outbound consumer calls whose responses come
back as ordinary HTTP client responses (not through any SBI server handler
below). The handlers marked (X) are the ones where another NF calls *into*
this AMF asynchronously/as a peer, and so actually correspond to a state
transition in that graph:
  - HTTPUEContextTransfer         -> CONTEXT_LOOKUP <-> AMF edge (this is the
    inbound side of "Namf ContextTransfer" when this instance is the OLD AMF)
  - HTTPHandleDeregistrationNotification -> UDM->Old AMF deregistration
    notify that drives old-AMF CLEANUP_REQUIRED (registration doc step 56)
  - HTTPN1N2MessageTransfer       -> SMF pushing NAS/N2 into
    SM_CONTEXT_PENDING -> INITIAL_CONTEXT_SETUP
  - HTTPSmContextStatusNotify     -> SMF async status feeding
    PDU_SESSION_REJECTED / cleanup
  - HTTPCreateSubscription        -> PCF Namf_EventExpose_Subscribe during
    POLICY_ASSOCIATING (registration doc step 62)
  - HTTPAmPolicyControlUpdateNotifyUpdate/Terminate -> PCF pushing policy
    changes that affect POLICY_ASSOCIATING / REGISTERED_CONNECTED
The rest are real endpoints but aren't on a path any edge in that graph
exercises, so hooking them adds volume without adding state-transition signal.
